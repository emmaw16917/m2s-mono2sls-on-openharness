01 · pipeline

四条线，加一段两基线优化

列内箭头是依赖顺序，虚线是跨线交接。事实库线和裁判线共享左边两列；设计/实现线等缺口清单与裁判冻结，验证/收尾线等打包产物。B0 之后优化段沿第 4 列继续：O1 出候选，dispatcher 串行派 owner 实现、O1M 测量、accept 保留/回退，复检后冻结为 B0P，O2 再在 B0P 上做局部优化。

02 · dispatch

“派 agent”到底派了什么

调度器本身不调用模型：它是一个确定性循环，从任务板挑出依赖已关闭、scope 不冲突、锁拿得到的任务，再为每个任务启动一个非交互的 OpenHarness 进程。worker 的全部输入是 prompt、权限覆盖和 MCP；全部输出是它 scope 内的文件加一次 submit_task。

03 · channels

它们怎么交流

没有 agent 之间的自由聊天。每一条交流都有确定的载体、方向和落盘位置。

files · 主通道

工作区文件与 scope

所有产物都落在 storage/、judge/、output/、verification/。每个任务只写自己的 scope，两个任务的 scope 前缀重叠就串行；双方都声明 shared_write 的共享文件（F2 的 analysis_report.json）是例外——写入由跨进程文件锁串行化。下游读上游写下的文件，检查也只读文件。产物即接口。

board · 控制面

任务板 br

任务、依赖边、状态、门都在这里。只有调度器读写任务板；worker 看不到它，也不需要它。谁阻塞谁、谁先跑，全由板上的依赖边决定。

worker → dispatcher

submit_task / report_blocked

worker 结束前调 submit_task 交工作报告；做不下去就 report_blocked，写明原因、证据和可疑模块。没有提交的进程退出按崩溃处理，不计入正常尝试。

mail · 公告

公告板 notices

调度器和 m2s-server 往 agent_mail 发 artifact（事实库升版本、产物就绪）和 spec-issue；所有角色都能读。事实库版本变化会让过期任务失效重跑。

mail · 讨论室

规格室 / 分诊室

J3 本身是普通 worker，不在房间里；只有它判出的 needs_ruling 差异（以及阻塞级 spec_issues）会开规格室，fact_error/case_error/mask_gap 由 dispatcher 直接回炉。房间回合是 ROOM-* worker 任务，顺序 proposer → architect → annotator（需要时）→ proposer，最多 2 轮。开房间需 M2S_ROOMS=1（或 mail 环境）；否则 RULE_J3 直接 spawn mode=ruling 的 architect。

rulings

record_ruling

architect 或异常处理者把“事实库答不了的问题”写成裁定：contract / implementation-trace / migration-change / spec-gap。带 deviates_from_monolith 的裁定要人确认才生效；裁定的粒度是 case#step。

handler

异常处理者 case

任务用尽尝试、裁判/增量/适配检查失败、B0 阶段复查，都会由调度器写一份 case 文件（含证据链）并派一个处理者 worker。它的决定只有四种：retry、reroute、escalate（交人）、ok（复查通过）。

human

人门 HUMAN_*

迁移偏离、修单体缺陷、工具改动、覆盖缺口等最终由人决定。人通过 resolve --accept / --reject / --reopen / --rework 作答，决定写进事件日志和报告；调度器据此继续、重做或退回。

state

事件日志 + 影子 git

coord/events.jsonl 是状态的唯一来源：每次派发、退出、检查、裁定、决定都追加一条。中断后按事件重放恢复，已启动的 worker 被“收养”；每次尝试另有影子 git 快照，可回滚。

locks

机器级资源锁

workers 槽限制并发数；docker-rie 让 J2 与所有 RIE 验证串行；aws-load-client 保证同一个时间只有一个 AWS 负载在跑。工作区级的 storage/.analysis_report.lock 让 F2 的多个包 annotator 串行地读-改-写同一份事实库；持锁进程死亡或 TTL 过期后锁可被回收。拿不到锁的任务只是在板上等。

05 · split

三种拆分粒度

拆分只改变“谁写哪块”，不改变每步的检查。子任务都是普通 agent 任务，只是 scope 更窄、函数列表更小；F2 的包任务共用一份文件，靠 shared_write + 跨进程文件锁并行；shared 子任务在所有子任务之后收口。O1C 是串行候选链，不是并行族。

族维度子任务写什么并行？收口
F2按工作包各自包的事实库条目；所有子任务写同一个 storage/analysis_report.json，每次 annotate 持锁读-改-写。并行（shared_write + 文件锁）F2-shared 汇总校验
G2按工作包storage/gaps/<包>.json，互不重叠。并行G2M 合并
J1按工作包judge/cases/<包>/，每个包只写自己的用例文件。并行J1-shared 写 fixtures/identities/faults + 整份检查
D1按领域verification/delta/events/<fn>/ 与 delta-<领域>-* 故障场景。并行V3 全量跑
I1按领域output/lambdas/<app>/<fn>/，每函数目录一个领域。并行I1-shared 共享层
O1C按候选每个候选一条 owner → O1M → accept；owner 只写自己的 scope（A1 蓝图、D1 测试、I1 代码、I2 模板）。串行（相对已接受基线逐个测）accept 保留或 revert
并行的上限是：3 个 worker 槽、scope 不重叠（或双方都把同一路径声明为 shared_write）、资源锁可用。F2 的包任务现在也并行：analysis_report.json 声明为 shared_write，三个 annotate 工具在 storage/.analysis_report.lock 下串行化读-改-写，_save 用 PID 唯一临时文件 + 原子替换。2026-11-24 的 coffee 真 LLM 实跑达到 3 路并发，F2 墙钟 54.6 min（串行约 117 min）。裁判冻结之后，任何拆分都不允许碰 judge/。O1C 的候选链故意不并行：每个候选的收益要相对“B0 + 已接受的候选”测，而且 accept 会移动 HEAD，并行会互相污染基线。
