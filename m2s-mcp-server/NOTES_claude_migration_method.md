## 文章方法摘要
- 核心：fix the process (loop), not the code；每阶段 实现→评审→修复，脚本当裁判。
- judge = 确定性工具（测试套件 / 编译器 / 场景 diff），agent 只负责写、审测试；judge 要在原代码上通过、在故意弄坏的代码上失败。
- rulebook：结构保持型 = 类型/惯用法对照表；重设计 = 设计文档；每个歧义点一条 policy。
- gap inventory：目标环境要求显式、原代码隐含的知识；必须在 rulebook 之后做。
- 压测 rulebook：小规模演练，rulebook 版 vs "资深工程师"版，第三个 agent 把 diff 变成新规则；产物丢弃。
- 全量：小模型实现、大模型评审；队列从磁盘生成（输出存在=完成）；`TODO(port)`；双对抗评审（各自独立上下文，引用规则）+ 第三方仲裁；反复出现的错误→改规则、重新生成该批次。
- 行为：原代码是唯一标准，任何行为变化都按 bug 处理；文章没有说"有意偏离"由谁批准。
- 性能：不是验收条件，只报告结果（收益主要来自换语言）；没有性能优化循环。

## 对照 m2s 的结论
1. **judge**：V 线（规格→用例，dynalite + 故障注入）、S5 H1（对比 v0）、AWS e2e。不足：
   - judge 本身没验证过（缺变异测试）；
   - 期望值来自 LLM 写的规格，而不是单体实际运行的结果；
   - H1 是和 v0 比，不是和单体比；
   - 本地模拟有盲区（TransactionConflict、CORS、IAM）。
2. **rulebook ≈** KB 模式 + 提示词 + blueprint + R1–R8；**gap inventory ≈** S0 标注、SI、K13、CORS、TZ。不足：
   - gap 是在每个应用里被动发现的；
   - spec_resolutions 只对单个 workspace 生效，没有沉淀成跨应用规则；
   - 没有压测 rulebook 的环节。
3. **裁决**：m2s 必须保留规格放宽和人工裁决机制，因为 serverless 不可避免要改变并发、一致性、重试等语义，文章没有覆盖这类问题。可借鉴：
   - 裁决结果写回规则并重新生成；
   - SI/REQ 必须引用规则或规格条目。
4. **性能**：S5 是文章没有涉及的部分，可作为差异化贡献。可借鉴：
   - 反复出现的优化前移到 S3 规则（例如 R1、R1b）；
   - 把相对单体和 v0 的性能回归设为验收条件。
5. **harness 也在演进**：现在是"运行内冻结（TOOLS gate）、运行间演进"。还缺：
   - harness 版本记录（工具 commit / 提示词 / 模型，例如 coffee 的 max/flash 混杂）；
   - 规则变化后重新生成所有应用（不能像 GM1–3 那样不回补）；
   - judge 和 rulebook 的修改分开管理（改 judge 要重新验证）。
6. **功能和实现轨迹的区分（候选方案）**：

   | 层 | 判据 | 谁可以改 |
   |---|---|---|
   | 必须保持 | 和**实际运行的单体**做差异比对 | 不可改 |
   | 可在声明范围内放宽 | 带标签的规格项（ordering / consistency_window / retry_idempotent…） | 只能经裁决通道，并沉淀成跨应用规则 |
   | 实现轨迹 | 前两层都没覆盖的部分 | S3–S5 自由改 |

   - 判定：第 1 层差异比对失败 = 没完成功能；第 1 层通过、只有轨迹不同 = 合法优化。
   - 规格版本在每次运行内冻结、运行间演进；单体差异比对同时用来检验规格本身。
   - 对应的现状局限：规格错误会传下去、过度规定（SI-1 排序）、规定不足（CORS、SI-4）、表达不了连续谱、不跨应用积累。

## 补充：其他实践文章可借鉴点（2026-10-16）
> Dehghani（数据归属、粒度）与 Prime Video（高频路径不拆多跳）两条：**暂存**，等新流水线大框架定下后再敲定落到 S1 gate 还是 architect 规则。
- **Google** (arXiv 2501.06972)：
  - 确定性工具负责定位（Kythe/Code Search，按 BFS 扩展三层）和验证（构建、单测、AST diff 检查多余改动）；
  - LLM 用小而聚焦的 prompt；
  - 人工评审是瓶颈，要主动控制产出速度；
  - 用端到端节省的时间衡量，目标 ≥50%。
- **Airbnb** (Enzyme→RTL)：
  - 每个文件走一个阶段状态机，状态印在文件里；
  - 带错误反馈的暴力重试胜过调 prompt；
  - 选对上下文（同目录的兄弟文件）比 prompt 措辞更重要；
  - 长尾用 sample→tune→sweep：抽 5–10 个失败样本，修共性问题，再全量重跑；
  - 收益趋平时转人工处理。
- **Dehghani** (martinfowler)：
  - 数据要跟着服务走（共享库是反模式）；
  - 先拆不需要回调单体的边缘能力，必须回调时经防腐层；
  - 黏性能力（如 session）要拆成领域概念；
  - 从 bounded context 大小的宏服务开始，避免贫血的 CRUD 服务；
  - 一步算完成 = 抽出服务 + 重定向调用方 + 删除旧路径。
- **Strangler fig** (OneUptime)：
  - 新旧系统并行调用、比对响应并记录延迟（shadow 比对）；
  - read-through 方式迁移数据；
  - 用 feature flag 灰度切换，保留旧系统 2–4 周作为回滚窗口；
  - 先迁低风险模块（不要先迁支付）。
- **Prime Video** (2023)：
  - 每秒多次状态转换的高频编排（Step Functions）撞上账户限额，中间数据经 S3 传递导致成本高；
  - 合并成单进程后成本降低 >90%；
  - 粒度要按调用频率和数据传输量逐案决定。

## 流水线 v2 讨论进展（2026-10-29）
**用户已同意**
- judge 不依赖 blueprint，用单体的术语表达，可以和 S1 同时开始建。
- 建 judge 时允许 V1 读单体代码：从代码里看出、规格里没有的规则，必须提成 spec-gap。
- `run_judge` 向实现线开放可见部分的完整用例（修改 K10），可以拿来做单元测试和集成测试；judge 文件对实现线只读。
  - **后续扩展**：保留一部分用例只在验收时运行，用两者通过率的差衡量是否针对用例写代码。
- 裁定记录从 `blueprint.metadata.spec_resolutions` 里拆出来，单独存放。
  - 纠正事实 → 修改单体事实库；
  - 决定要不要保留某个单体行为 → 写进裁定记录。
- serverless 新增测试的期望值：能对照单体的，就取"单体执行一次的效果"。
- D1c：测试数据按单体表结构写，architect 产出单体表结构到目标表结构的映射（适配层），V2 用"写过去再读回来"检查映射。
- D1d：身份映射（单体 JWT ↔ Cognito claims），由工具分别获取两边的凭证；登录和注册接口自身归入"迁移带来的变化"。

**分层产物**
- harness（跨应用、带版本号）= 工具 + 提示词 + rulebook + 模型；rulebook 只在 harness 升级时修改。
- 每个应用：
  - 单体事实库：analysis_report，在 J3 被纠正；
  - judge：J5 冻结，带版本号；
  - gap inventory；
  - blueprint + 适配层映射；
  - DECISIONS.md：主动做的设计决定；
  - 裁定记录：对提出的问题做的仲裁；
  - 各 agent 的产物和日志。
- 跨应用汇总**不单独维护**（用户 2026-10-29 提出），在 harness 升级时用脚本从各应用的记录生成，和 gap inventory 一样。
  - 运行过程中也不读跨应用汇总，避免同一版 harness 下应用之间互相影响。
  - 前提是各应用的记录要能保存下来（见待拍板）。

**待拍板**
- 单体有 bug 时，默认以单体为准，偏离必须经过裁定。
- 每次运行结束时，工具把这个应用的裁定记录、gap inventory、perf_report、harness 版本号**机械归档**到仓库（只追加），升级 harness 时由汇总脚本读取；ledger 以后改成由归档生成的一个视图。
- 性能改动：
  - 小范围改动：judge + 复用 v0 的新增测试 + H1 + 给改动到的行补用例；
  - 架构改动：回到 S1 重新生成，judge + 重建受影响部分的新增测试，H1 不适用。
