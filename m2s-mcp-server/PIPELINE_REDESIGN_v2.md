## 0. 一页概览

**M2S 做什么**：输入一个单体 Web 应用（Express 或 Flask，数据存在 DynamoDB 或 MongoDB），由一组 LLM agent 自动产出等价的 AWS Serverless 版本：每个接口一个 Lambda 函数，前面是 API Gateway，后面是 DynamoDB 和 SQS，整体用一份 SAM 模板描述。之后再在保证行为不变的前提下做性能优化。

**v2 的三个核心想法**：

1. **先建裁判，裁判以单体为准。** 迁移开始之前，先为每个应用建一套"裁判"（测试用例 + 期望结果）。期望结果来自**实际运行单体**，而不是由 LLM 根据代码推断。裁判本身也要经过检验：在故意弄坏的单体上运行时必须报失败。
2. **知识分层，修流程而不修产物。** 跨应用通用的"规则手册"只在升级流水线时修改；每个应用特有的问题记进这个应用自己的"缺口清单"和"裁定记录"。反复出现的问题，经人工批准后才晋升为通用规则，然后用新版流水线重新生成。
3. **用三层观测区分"功能没做完"和"实现方式变了"。** 外部可观察的行为分为"必须保持"和"可在声明范围内放宽"两层，由裁判判定；其余的内部实现细节属于"实现轨迹"，可以自由修改。

**流程总览**（每个方框是一个模块，详见 §4）：

```
            ┌────────── 事实线 F ──────────┐
单体代码 ──► F1 结构提取 → F2 语义标注 → F3 出处检查 ──► 事实库
                                                    │
                       ┌────────────────────────────┼────────────────────────┐
                       ▼                            ▼                        ▼
                G1/G2 缺口盘点             J1…J6 建裁判（以单体为准）      （裁判不依赖蓝图，
                       │                            │                        与设计并行）
                       ▼                            │
                A1/A2 蓝图设计 ◄── 事实修正同步 ─────┤
                       │                            │
                       ▼                            │
                D1 增量测试设计（看不到代码）        │
                       │                            │
                       ▼                            ▼
                I1 写代码 ── run_judge 自测 ── 冻结的裁判（只读）
                I2 写模板 → I3 静态一致性检查
                       │
                       ▼
                V1 适配映射检查 → V2 裁判验收 → V3 增量测试验收 → V4 分诊
                       │

                O1 诊断 → O2 小范围优化（逐个判决）/ O3 架构改动申请（回到 A1）/ O4 交人裁定
```

## 1. 背景

### 1.1 输入、输出和范围

- **输入**：单体应用的源代码目录。
- **输出**：
  - serverless 版本的代码（每个函数一个目录）和 SAM 模板；
  - 每个阶段的工作报告、验收判定、性能优化报告、最终报告。
- **范围**：迁移和验收**离线完成**，不部署到 AWS。正确性验证都在本机模拟环境中进行。真实 AWS 上的延迟和成本测量作为单独的实验，不属于流水线。

当前的 7 个基准应用：

| 应用 | 框架 | 数据存储 | 鉴权 |
|---|---|---|---|
| bookstore、coffee、todo | Express（Node.js） | DynamoDB（aws-sdk v2） | 应用自己签发 JWT |
| airline-booking、ecommerce、shopping-cart | Flask（Python） | DynamoDB（boto3） | 应用自己签发 JWT |
| acmeair | Express（Node.js） | MongoDB | 应用自带的认证服务 |

### 1.2 运行环境

| 组成 | 说明 |
|---|---|
| **OpenHarness** | agent 运行框架。一个**编排 agent**（下文称"主 Agent"）按编排协议依次派发各个**子 agent**，子 agent 之间通过工作区里的文件传递状态 |
| **编排协议** | OpenHarness skill `m2s-migrate`：规定模块顺序、派发要求、复核方式、回炉规则 |
| **子 agent 定义** | `m2s-mcp-server/agents/*.md`，运行时同步到 `~/.openharness/agents/` |
| **知识库（KB）** | `.openharness/skills/` 下的几个 skill，子 agent 按需加载 |
| **MCP 工具** | 本地 MCP 服务 `m2s-server`（`m2s-mcp-server/server.py`）：分析、标注、检查（gate）、验证、性能判决等工具，都是确定性脚本 |
| **hook** | `hook_guard_mcp_auth.py`（工具调用前：拦截对本地服务的无意义认证调用）；`hook_audit_subagent_stop.py`（子 agent 结束时：写一行审计记录） |
| **本机验证环境** | Docker 里的 **Lambda RIE**（AWS 官方 Lambda 运行时模拟器）；**DynamoDB Local**（AWS 官方本地数据库）；一个**记录 + 故障注入代理**（`verify-tools/controller.js`），函数里的 SDK 调用都经过它：它记录每次调用，按用例配置注入故障，再转发给 DynamoDB Local。没有 Docker 时退回到本机 Node 或 Python 直接运行 |
| **工作区（WS）** | 每个应用每次运行一个目录 `Mono2Sls-artifacts/M2S/runs/<应用>-<运行名>/`，里面是一个独立的 git 仓库 |

### 1.3 为什么要做 v2

v1 已经能把 7 个应用都迁移并验收通过，但暴露出四个结构性问题：

1. **期望结果没有参照物。** 测试的期望值是 LLM 根据它对单体代码的理解推断出来的。理解错了，测试和实现会错得一致，测试照样通过。实际出过的例子有：漏掉"请求体不是 JSON 时返回 400"、漏掉 CORS 响应头。
2. **裁判本身没被检验过。** 从没验证过"测试能不能抓住真正的错误"。
3. **经验不能跨应用积累。** 一个应用里对某个问题的裁定只对这个应用生效。修复也不会回补到其他应用，导致各应用的结果对应不同版本的流水线。
4. **"功能"和"实现方式"的界限靠事后修补。** 测试曾把单体的实现细节（例如"先读一次再读一次"）当成必须保持的行为，挡住了合理的优化，只能事后放宽。

## 2. 术语

| 术语 | 含义 |
|---|---|
| **单体（M）** | 迁移前的原程序，是行为的唯一标准 |
| **目标版本** | 迁移得到的 serverless 版本 |
| **基线版本 B0** | 第一个通过验收的目标版本，在工作区 git 里打 tag `B0` |
| **优化版本** | B0 之后，每保留一个性能改动就提交一次 |
| **外部效果** | 从系统外部能观察到的结果：HTTP 响应（状态码、响应体、响应头）、**写操作之后调用读接口读回的数据**、对外发出的消息和调用 |
| **实现轨迹** | 外部效果以外的内部细节：数据库调用的次数和顺序、串行还是并行、内部数据怎么组织 |
| **三层观测** | **P 层（必须保持）**：必须和单体一致。**R 层（可放宽）**：允许和单体不同，但只能在裁定声明的范围内，比如"结果顺序不作要求""允许读到 N 秒内的旧数据"。**T 层（实现轨迹）**：不做判定 |
| **事实库（FB）** | 对单体做静态分析得到的事实：路由、鉴权、请求和响应、业务规则、数据访问、表结构等。每条都带出处（文件、行号） |
| **裁判（J）** | 每个应用一套测试用例 + 期望结果。期望结果来自单体的实际运行；建好并检验后**冻结**，带版本号 |
| **增量测试（Δ 测试）** | 专门测试 serverless **新增**行为的用例，比如消息重复投递时的幂等、批处理部分失败。单体里没有这些行为，所以裁判覆盖不到 |
| **适配映射（AD）** | 让同一套裁判能作用到目标版本的映射：**数据映射**（单体表结构 → 目标表结构）和**身份映射**（单体的登录凭证 → serverless 的鉴权凭证） |
| **规则手册（RB）** | 跨应用通用的迁移知识：怎么分解、怎么写代码、怎么写模板、哪些优化规则可用，以及裁定先例 |
| **缺口清单（GI）** | 每个应用一份：这个应用里，单体隐含、serverless 必须显式处理、规则手册又没覆盖到的语义 |
| **蓝图（BP）** | serverless 版本的设计：函数划分、API 类型、表设计、通信机制、鉴权 |
| **决策记录** | `DECISIONS.md`：设计者**主动做的决定**和依据 |
| **裁定记录（RL）** | 对别人**提出的问题**做的仲裁：问题、可选方案、谁裁定的、结论、依据 |
| **规格问题（SI）** | 某个 agent 发现规格写错、自相矛盾或缺失时提出的问题，进入裁定通道 |
| **裁定通道** | 处理规格问题和权衡问题的固定路径：由谁裁定、记在哪里、影响什么（§4.12） |
| **证据库（EA）** | 仓库里只追加的归档，存放每次运行的裁定记录、缺口清单、性能报告等，供流水线升级时汇总 |
| **流水线版本 H_n** | 工具 commit + agent 定义 + 规则手册 + 模型，四者合起来的版本。每次运行都记下它 |
| **gate** | 由脚本执行的检查（MCP 工具 `run_gate`），是推进到下一个模块的权威依据。agent 自己说"完成了"不算数 |
| **回炉** | 检查不通过时重新派发某个模块 |

## 3. 资产分类：跨应用共用 / 单应用指导 / 单应用产物

### 3.1 三类资产的区别

| 类别 | 作用 | 生命周期 | 谁能改 |
|---|---|---|---|
| **跨应用共用（流水线本身）** | 决定"怎么迁移"：工具、agent、规则 | 跨越多次运行；只在升级流水线时修改 | 只有人（经 §5 的升级流程） |
| **单应用指导内容** | 决定"这个应用要迁成什么样"：事实、缺口、裁判、设计、裁定 | 在单次运行中产生和修订，到某个点冻结 | 指定的模块，经指定的通道 |
| **单应用产物** | 运行的结果：代码、模板、判定、报告 | 由各模块产出，可以重新生成 | 产出它的模块 |

### 3.5 单次运行中，指导内容和产物怎么产生、怎么完善

1. **流水线在运行内冻结。** M0 记下版本戳；任何 agent 都不能修改工具、agent 定义和规则手册。每个 gate 都检查一次，发现修改就撤销，并把这个模块判为阻塞，交给人。
2. **指导内容只能经指定通道修订：**
   - **事实错误**（单体实际上不是这样）：退回 F2 修正事实库，并重新做出处检查。这**不需要裁定**，因为单体的行为是什么是客观事实。
   - **需要做决定的问题**（单体有 bug 是否照搬、某个行为能否放宽）：进入裁定通道，结果追加到裁定记录。
   - **设计决定**：只由 A1 写进蓝图和决策记录。
3. **冻结点。** 裁判在 J6 冻结。之后发现裁判本身有问题，只能由人批准升级裁判版本，并重新验收。蓝图和适配映射在 B0 时定稿；之后的架构改动走 O3，开启新的一轮设计、实现和验收。
4. **运行内不跨应用参考。** 运行过程中不读其他应用的裁定和证据库，保证同一版流水线下各应用的实验条件相同。
5. **运行结束时机械归档。** C2 把这次运行的指导内容和关键产物复制到证据库。

### 3.6 跨应用运行之后，共用内容怎么升级

概要（详细流程见 §5）：

- 汇总证据库，找出反复出现的裁定、缺口和失败模式；
- 满足晋升条件、经人批准的，进入规则手册；
- 在 1–2 个试点应用上压测新规则；
- 发布新版流水线，先在少数应用上重跑验证，再推广到全部应用；
- 论文主结果用最终冻结的版本统一重跑。

## 4. 单次运行：逐模块说明

### 4.0 全局约定

- **编排**：主 Agent 按本章的顺序派发模块。标为"工具"的模块由主 Agent 直接调用 MCP 工具完成，标为"agent"的模块派发对应的子 agent。
- **复核**：每个 agent 模块结束后，主 Agent 亲自运行对应的 gate 或判定工具，**以工具结果为准**，不以 agent 的自述为准。
- **回炉上限**：
  - agent 内部最多自查 3 次；
  - 主 Agent 对同一模块最多重新派发 2 次；
  - 验证线修自己的测试资产，每轮最多 2 次，单独计数；
  - 裁定往返最多 2 轮。
  - 用满仍不通过：停止，把完整报告交给人。
- **出题和答题分开**：
  - 增量测试（D1）在代码出现之前设计，设计者看不到实现；
  - 裁判对实现线**开放可见**（可读、可运行，不可修改）；
  - 实现线的提示词里不写增量测试的内容。
- **网络抖动**：每次派发都提醒子 agent，遇到偶发的连接错误重试 1–2 次，不要直接放弃。

每个模块按以下四项说明：
- **输入**；
- **输出**（内容和存放位置）；
- **反馈**（反馈什么、反馈给谁）；
- **过程**（执行者，用到的知识库、MCP 工具、hook 和 gate）。

"状态"一栏标明这个模块是现有、修改还是新增。

### 4.4 裁判线 J：建立裁判（以单体为准）

裁判线只依赖事实库和单体，**不依赖蓝图**，所以可以和设计（A1）同时进行。

#### J1 黑盒用例设计

| 项 | 内容 |
|---|---|
| 状态 | 修改（v1 的测试设计改为以单体为对象） |
| 输入 | 事实库（只看事实库，不看代码，这样事实库的错误才会在 J3 暴露出来）、已有的裁定记录 |
| 输出 | `judge/cases/<接口>/<用例>.json`，每个用例包括：<br>- HTTP 级请求、身份（用户别名，如 `u1`）；<br>- 前置数据：引用 `judge/fixtures/`，**按单体的表结构**写；<br>- 按事实库推出的预期结果；<br>- 事实库出处；<br>- 分层标签初值（P 或 R）。<br>另有 `judge/faults/`：故障场景，比如某条数据上的操作失败、限流、超时 |
| 反馈 | 写不出预期结果（事实库自相矛盾或有缺漏）→ 提规格问题：属于事实问题的退回 F2；需要做决定的进入裁定通道 |

#### J2 运行单体

| 项 | 内容 |
|---|---|
| 状态 | 新增 |
| 输入 | 单体代码、建表脚本、裁判用例和测试数据 |
| 输出 | - `judge/oracle_expected.json`：每个用例在单体上的实际外部效果（响应、写后读回的数据、对外的调用）；<br>- `judge/masks.json`：易变字段屏蔽表；<br>- `judge/fault_baseline_monolith.json`：单体在各故障场景下的行为；<br>- `judge/coverage_monolith/`：单体的分支覆盖率 |
| 反馈 | 单体起不来、用例无法执行 → 退回 J1 修用例（验证线自修，每轮最多 2 次）；环境问题报给人 |
| 过程 | 执行者：主 Agent（工具）。MCP 工具：新增 `run_monolith`，复用现有的记录 + 故障注入代理和 DynamoDB Local |

`run_monolith` 的具体做法：
- 单体作为宿主机进程运行：Node 直接运行，Python 用 conda 环境；数据库在 Docker 里；统一设置 `TZ=UTC`。
- 让单体连接本地数据库：
  - boto3 通过环境变量 `AWS_ENDPOINT_URL_DYNAMODB` 指向代理；
  - aws-sdk v2 用启动预加载脚本设置 endpoint（**已验证**，2026-11-01，见 Q4）；
  - acmeair 连接容器里的 MongoDB，只做接口层比对。
- 身份：调用单体的登录接口，或用配置里的密钥直接签发令牌。
- 每个用例**运行两遍**，两遍之间不一致的字段自动进入屏蔽表（uuid、时间戳、令牌等）。屏蔽时把易变值换成符号（如 `<uuid#1>`），保留它们之间的对应关系（见 Q11）。
- 覆盖率：按用例分别记录。Node 在单体进程内用 inspector 的 `Profiler.takePreciseCoverage`（每次取数后计数清零，已验证）；Python 用 coverage.py 的 `switch_context`（待验证）。

#### J3 规格对账

| 项 | 内容 |
|---|---|
| 状态 | 新增 |
| 输入 | 每个用例按事实库推出的预期结果，以及单体的实际输出 |
| 输出 | `judge/reconcile.json`。一致的用例，期望结果定为单体的实际输出（屏蔽易变字段后）；不一致的用例列为差异，每条写明属于哪一类 |
| 反馈 | - **事实错误**（单体就是这样，事实库写错了）→ 退回 F2 修正事实库，重做 F3；<br>- **需要做决定**（单体本身有 bug，或者某个行为能否放宽）→ 进入裁定通道。默认规则是**以单体为准**，偏离单体必须有裁定。<br>事实库被修正后，如果涉及蓝图已经引用的事实，通知 A1 复查 |
| 过程 | 执行者：主 Agent（工具）+ agent。MCP 工具：新增 `reconcile_spec`。agent `m2s-verifier` 负责给差异分类，最多 2 轮 |

| 项 | 内容 |
|---|---|
| 状态 | 新增 |

| 反馈 | 从代码中看出、事实库里没有的规则 → **必须**作为规格问题（缺失类）提出，退回 F2 补进事实库，不能只写进用例 |

#### J5 裁判自检（变异检验）

| 项 | 内容 |
|---|---|
| 状态 | 新增 |
| 输入 | 裁判、单体代码、变异算子表 |
| 输出 | `judge/judge_validation.json`：生成了哪些变异体、哪些被裁判抓住、检出率、哪些没被抓住 |
| 反馈 | 没被抓住的变异体 → 回到 J4 补用例（最多 2 轮）。如果变异体其实不改变外部效果（等价变异），由 verifier 标记后排除 |

初始变异算子：删掉一个分支、改一个状态码、删掉一个响应字段、去掉一次写操作、把判断条件取反、去掉鉴权检查、把并行改成串行（检验裁判是否误判实现轨迹）。

单体覆盖率（J2）和变异检出率（J5）合起来，作为**裁判强度**的两个指标。

#### O2 小范围改动（只动实现轨迹）

| 项 | 内容 |
|---|---|
| 状态 | 现有，新增两项检查 |
| 输入 | 改动请求、B0（或上一个优化版本）、冻结的裁判、增量测试、B0 的故障行为基准 |
| 输出 | 每个改动的判决 `perf/verdicts/*.json`；保留的改动各提交一个 commit；`output/perf_report.json` |
| 反馈 | - 需要放宽某个行为才能做的改动 → 进入裁定通道。如果获批，影响 R 层，需要由人批准升级裁判版本，并在 B0 上重新验收；<br>- 有得有失的改动 → 交给 O4；<br>- 和 B0 行为不一致 → 视为代码问题，修 1 次，还不行就撤销；<br>- 和 B0 一致但有用例失败 → 视为测试问题，交给验证线复查 |
| 过程 | 执行者：agent `m2s-perf-optimizer` + 工具 |

O2 对每个改动依次做以下检查，任何一项不通过就撤销：
1. **裁判**和**受影响函数的增量测试**都要通过（`run_judge`、`run_validate`）；
2. **和 B0 的行为一致性**：在同一组故障场景下，比较改动前后的调用集合，以及返回值、错误、批处理失败清单（`run_equivalence`）；
3. **改动到的代码行**必须被测试执行到，没执行到的先补用例（`run_coverage(changed_since)`），这能覆盖小改动带来的新分支，比如事务冲突处理、缓存过期；
4. **改动范围检查**（新增，提议）：改动只能落在请求里声明的函数中（参照 Google 的 AST diff，新增工具 `check_change_scope`）；
5. **性能判决**：在 Lambda RIE 里交替测量改动前后的热调用耗时、初始化耗时和成本。延迟分别取 5、10、15ms 三档模拟数据库往返（0ms 只作参考），三档都更好、并且热调用 CPU 不超过原来 2 倍才保留；成本按 10ms 档计算（`run_rie_verdict`）。只改配置的改动（如 R5 arm64）用 `run_config_verdict`。

### 4.11 失败分诊

| 信号 | 交给谁 |
|---|---|
| gate 不通过 | 产出那个文件的模块（agent 先自查，主 Agent 最多重派 2 次） |
| 适配映射检查不通过 | 映射写错 → A1；读接口代码写错 → I1 |
| 裁判 P 层失败 | 先判断原因：handler 逻辑问题 → I1；模板问题 → I2；设计问题 → A1。如果认为是裁判的期望本身有争议 → 进入裁定通道，**分诊过程不能改裁判**，只能由人批准升级裁判版本 |
| 增量测试失败 | 代码问题 → I1；测试资产问题 → 验证线自修；蓝图问题 → A1 |
| 优化后和 B0 不一致 | 代码问题，修 1 次，否则撤销 |
| 优化后和 B0 一致但用例失败 | 测试问题，交给验证线复查 |
| 机械信号：mock 未覆盖、模块导入失败、SDK 解码错误 | 分别是测量工具、打包、mock 数据结构的问题 |
| 判断不了 | 标为"未定"，交给人，不去猜 |

退回实现线时，转达的内容是：失败的函数、对应的事实库或规则出处、期望怎样、实际怎样。裁判用例对实现线是可见的，可以直接引用。

### 4.12 裁定通道

| 问题类型 | 裁定者 | 记在哪里 | 影响 |
|---|---|---|---|
| 事实错误（单体实际上不是这样） | 不需要裁定，由 F2 修正 | 事实库 | 用例的事实出处和期望 |
| 单体自身的缺陷是否照搬 | 默认照搬单体；要偏离，由 architect 提出、人确认（提议） | 裁定记录 | P 层的期望 |
| 某个行为能否放宽（顺序、新旧程度、多种可接受结果） | architect | 裁定记录 | R 层的判定范围 |
| 缺口怎么处理 | architect，写进决策记录；有争议时转为裁定 | 决策记录 / 裁定记录 | 蓝图、增量测试 |
| 性能上有得有失 | 人 | 裁定记录 | 是否保留这个改动 |
| 架构改动申请 | architect 或人 | 裁定记录 | 开启新一轮设计 |

每条裁定记录包括：编号、提出模块、问题、可选方案、裁定者、结论、类别（`contract` / `implementation-trace` / `migration-change` / `spec-gap`，以及放宽的类型）、影响的用例和观测层、依据、时间。往返最多 2 轮，之后仍未解决的交给人。

## 5. 跨运行：流水线升级（U1–U6）

| 步骤 | 输入 | 输出 | 执行者和工具 |
|---|---|---|---|
| **U1 汇总** | 证据库中自上次升级以来的全部归档 | 候选清单：<br>- 同类裁定；<br>- 同类缺口和新类别候选；<br>- 性能规则的命中、保留、撤销统计；<br>- 各模块失败的聚类；<br>- 裁判强度指标 | 新增脚本 `aggregate_evidence` |
| **U2 晋升评审** | 候选清单 | 获批的规则手册条目，每条带编号、适用条件、做法、证据来源；能机械化的同时加一个 gate 检查 | 人。晋升条件（提议）：≥2 个应用出现、形态相同、都被接受、没有反例 |
| **U3 压测新规则** | 获批条目、1–2 个试点应用 | 规则修正 | - **设计层**：2 个对抗评审在各自独立的上下文里攻击试点应用的蓝图和架构规则，每条意见引用规则编号，第三个 agent 仲裁（新增 agent，提议）；<br>- **代码层**：同一个函数，按规则手册写一版，再"像资深 serverless 工程师那样"自由写一版，由第三个 agent 把差异提炼成规则候选；<br>- 最后在试点应用上跑完整流水线，用裁判检验。<br>演练产出的代码一律丢弃，只保留规则 |
| **U4 发布** | 修正后的规则手册、工具、agent 定义 | 新版流水线 H_{n+1}：提交、更新版本记录、同步 agent 定义、写变更说明 | 人 |
| **U5 回补** | H_{n+1} | 先在 2 个受影响的应用上重跑，确认没问题后，再推广到全部应用（"抽样 → 调整 → 全量"） | 人 + 流水线 |
| **U6 统一重跑** | 最终冻结的版本 H_final | 论文主结果：所有应用用同一版本重跑。演进过程另作为一个实验报告 | 流水线 |

几点说明：
- **规则手册和裁判分开管理。** 规则手册属于流水线；裁判属于应用。如果修改的是建裁判的工具（`run_monolith`、变异算子表），所有应用的裁判都要重新做 J5 检验。
- **只在升级时汇总。** 汇总不需要当时的上下文。真正需要当时记下来的是决定的理由，这已经在各应用的决策记录和裁定记录里。

## 6. 实验稳定性约定

- 一次运行内，流水线版本固定，由每个 gate 检查。
- 运行过程中不读其他应用的裁定和证据库。
- 裁判在 J6 冻结。所有判定结果都带上流水线版本和裁判版本。
- 换模型等同于换流水线版本，必须记录。（v1 曾出现同一个应用前后用了不同模型的情况。）
- 判定只认工具的输出，不认 agent 的自述。
