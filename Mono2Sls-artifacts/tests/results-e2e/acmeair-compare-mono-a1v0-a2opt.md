# Acme Air：单体 vs a1 v0 vs a2 优化版（AWS 同区域实测）

2026-10-12。本报告比较迁移前（单体）、第一次迁移的直接产物（a1 v0：未经 S5 优化）和当前流水线的最终产物（a2 优化版），用来回答"从首个可用迁移版本到现在，整条流水线的改进带来了多少收益"。

数据来自两次实测：`acmeair-ec2-ab/`（2026-10-09，单体 + a1 各版本）和 `acmeair-ec2-a2/`（2026-10-12，单体 + a2 各版本）。两次的测试设置、数据量和负载完全相同，单体在两次里各测了一遍，作为跨日期对照。同一批数据里的 a1 v0-http 和 a2 v0 两个中间版本，在第 3 节用来拆分各项改进的贡献。

## 1. 测试套件与方法

### 1.1 测试套件

Acme Air 官方性能测试驱动 **acmeair-driver**：JMeter 脚本 `AcmeAir.jmx`，附带官方 JMeter 扩展函数（生成航班日期、解析航班查询结果、选择要取消的预订）。脚本与单体同一提交（acmeair-nodejs `11fa31a`），未做修改。

脚本模拟一位顾客的完整会话，每个线程循环执行：

| 步骤 | 请求 | 接口 | 每轮次数 |
|---|---|---|---|
| 1 | Login | `POST /rest/api/login` | 1 |
| 2 | View Profile Information | `GET /rest/api/customer/byid/{user}` | 按比例，约 25% 的轮次 |
| 3 | Update Customer | `POST /rest/api/customer/byid/{user}` | 同上，紧跟步骤 2 |
| 4 | QueryFlight | `POST /rest/api/flights/queryflights`（往返） | 5 |
| 5 | BookFlight | `POST /rest/api/bookings/bookflights` | 查到可订航班时 1 次（单体约 96% 的轮次，serverless 约 82–85%，取决于查询结果） |
| 6 | List Bookings | `GET /rest/api/bookings/byuser/{user}` | 1 |
| 7 | Cancel Booking | `POST /rest/api/bookings/cancelbooking` | 只在该顾客已有 2 个以上预订时 |
| 8 | logout | `GET /rest/api/login/logout` | 1 |

用户从 1 万个顾客中随机抽取。会话靠 `sessionid` cookie 维持，和单体的登录契约一致。每遍约 1,870 个请求，其中 QueryFlight 1,000 个，占 54%。

### 1.2 测试环境

| 项目 | 设置 |
|---|---|
| 区域 | us-east-1，压测机与被测服务同区域 |
| 压测机 | EC2 t3.small，us-east-1a，JMeter 非 GUI 模式 |
| 并发与轮次 | 10 个线程 × 20 轮（`-JNUM_THREAD=10 -JLOOP_COUNT=20`）；闭环负载，每个线程等上一个响应回来才发下一个 |
| 数据 | 官方 loader 装载：10,000 顾客、14 个机场、394 个航段、5,122 个航班（`MAX_DAYS_TO_SCHEDULE_FLIGHTS=13`，保证往返查询有回程） |
| 遍数 | 每个版本两遍：第 1 遍包含冷启动和冷缓存，第 2 遍为热态 |

### 1.3 被测版本

| 版本 | 部署 | API 入口 | 性能优化 |
|---|---|---|---|
| **单体** | EC2 t3.small（Node 22 + MongoDB 4.4，同一台机器，同 AZ） | 应用直接监听 9080 端口 | — |
| **a1 v0** | Lambda（nodejs22.x、arm64、512 MB）+ DynamoDB 按需计费；工作区 acmeair-a1，标签 v0（`9fff1aa`） | REST API（`AWS::Serverless::Api`，边缘优化，经 CloudFront） | 无：迁移验收通过后、S5 之前的版本 |
| **a2 优化版** | 同上；工作区 acmeair-a2，提交 `838407b` | HTTP API（`AWS::Serverless::HttpApi`，区域端点，payload 1.0，由 S1 决定） | S5 规则 R8：`flights-query` 对航班和航段两张表加内存缓存（TTL 1200 秒，最多 10 万条，依据 S1 写入的 bounded_staleness 契约 SI-23） |

a1 与 a2 是同一个单体经流水线两次独立迁移的产物。两者之间的差别包括：
- API 类型：a2 的流水线在 S1 决定 API 类型（gate AT1/AT2），选了 HTTP API；
- 优化：a2 有 R8 缓存，a1 v0 没有任何优化；
- 代码：每个函数都由 S2 重新生成，实现细节不同（例如 a2 v0 的 `bookings-create` 本来就并行写两条预订）。

### 1.4 测量了什么

- **端到端延迟**：压测机 JMeter 记录的每个请求耗时（JTL），统计 p50、p90、p99 和吞吐量。
- **每接口延迟**：按请求类型分别统计。如果一个请求的耗时窗口内完整包含一次 Lambda 冷启动（INIT_START 到对应的 REPORT，允许 100ms 时钟误差），它就算冷启动样本，不计入每接口的 p50/p90，只单独计数。
- **服务端时间**：
  - 单体：morgan 访问日志记录的每个请求响应时间。
  - Serverless：Lambda REPORT 中的 Duration 和 Init Duration；API Gateway 访问日志中的 responseLatency（请求进入网关到响应离开）和 integrationLatency（网关看到的 Lambda 调用耗时，含调用开销）。
- **资源与费用**：Lambda 调用次数和 GB-秒、DynamoDB 消耗的读写容量单位（RRU/WRU，CloudWatch 按分钟统计，各遍放在不同的分钟里）、按 us-east-1 公开价格计算的费用（REST API 每百万请求 3.5 美元，HTTP API 1.0 美元）。
- **正确性**：所有版本两遍都是 0 错误。压测前后用 `config/count*` 接口核对数据量，四次装载结果一致。

## 3. 数据解读

**1. 从 a1 v0 到 a2 优化版，热态延迟下降约三分之一，所有接口都受益。**
热态端到端 p50 从 41ms 降到 28ms（−32%），p90 从 61ms 降到 44ms（−28%），p99 从 138ms 降到 85ms（−38%）。闭环负载下吞吐由延迟决定，从 111 升到 130 req/s（+17%）。七个有足够样本的接口全部变快，降幅 6–17ms。

**2. 改进可以拆成三步，每一步都有同条件的实测数据。**
两次实测中还各有一个中间版本：a1 v0-http（只把 a1 v0 的 REST API 换成 HTTP API，代码不变）和 a2 v0（a2 的迁移产物，未经 S5 优化）。按热态端到端 p50 依次排列：

| 步骤 | 版本 | p50 ms | 变化 | 改进内容 |
|---|---|---|---|---|
| 起点 | a1 v0 | 41 | — | — |
| ① | a1 v0-http | 36 | −5 | API 类型：REST（边缘优化）→ HTTP API |
| ② | a2 v0 | 34 | −2 | 重新迁移：S1 直接选定 HTTP API，代码重新生成 |
| ③ | a2 优化版 | 28 | −6 | S5 规则 R8：航班查询缓存 |

- **① API 类型（−5ms，所有接口）。** 网关自身耗时从 4ms 降到 1ms，网关之外从 6ms 降到 3ms。前者是 HTTP API 比 REST API 轻；后者是 a1 的 REST API 为边缘优化型，请求要绕经 CloudFront，HTTP API 则是区域端点。除 FlightsQuery 和 BookingsCreate 外，各函数的执行时间在 a1 v0 与 a2 之间相差都在 ±1ms 以内，所以这些接口省下的时间都在网关层。
- **② 重新迁移的代码差异（−2ms，集中在 BookFlight）。** a2 v0 的 `bookings-create` 本来就把往返两条预订并行写入（S5 规则扫描记录"v0 已用 Promise.all"），函数执行时间从 17.5ms 降到 13.7ms。这正是 a1 由 S5 用规则 R1 才补上的优化，a2 在迁移阶段就做到了。所以 BookFlight 的降幅（−11ms）比只受网关影响的接口（−6 到 −8ms）多出约 3–4ms。
- **③ R8 缓存（−6ms 整体，只作用于 QueryFlight）。** FlightsQuery 执行时间从 24.9ms 降到 13.9ms，DynamoDB 读容量少了 23%，QueryFlight 端到端降 17ms，是网关层降幅的两倍多。QueryFlight 占全部请求的 54%，因此它对整体 p50 的贡献最大。第 1 遍 FlightsQuery 的热调用仍有 24.2ms，说明每个新执行环境都要从空缓存开始预热。

**3. 与单体的差距缩小了，但仍是一个数量级。**
单体热态 p50 为 2ms：a1 v0 是它的约 20 倍，a2 优化版约 14 倍。剩下的差距来自架构，不是代码质量：
- 单体处理一个请求的服务端时间只有 0.7–2.5ms，数据库和应用在同一台机器上，没有网络往返。
- Serverless 每个请求至少经过 API Gateway → Lambda → DynamoDB 三跳网络。即使函数只做一次 DynamoDB 读取，Lambda 执行时间也有 7–10ms；再加上约 10ms 的调用开销（integration 24ms 减去函数执行时间）和约 4ms 的网关与网络开销。
按现有的优化规则，剩余空间主要在 DynamoDB 调用次数和串行深度。R1b（往返查询的去程和回程同时读）测得关键路径可再减约 8ms，但只在缓存未命中时生效；这次因为规格缺少 `error_propagation` 标注而没有应用。

**4. 冷启动是 serverless 独有的尾延迟来源，两版之间没有差别。**
两个版本第 1 遍各有 25–27 次冷启动，Init Duration 约 0.3 秒，第 1 遍 p99 达 550–630ms；单体两遍的 p99 都在 10ms 以内。a2 没有针对冷启动做任何改动，两版的 init 时间相近，属于预期。要减少冷启动影响，需要预置并发、缩小部署包、调整内存等专门手段，不在本次比较范围内。

**5. 费用：每请求成本下降 58%，但持续负载下仍高于单体。**
- a1 v0 每百万请求 4.42 美元，a2 优化版 1.85 美元。下降主要来自 API Gateway 换型（每百万请求 3.5 → 1.0 美元）；另外缓存让 DynamoDB 读费用下降约 9%，Lambda 计算量下降 18%。
- a1 v0 的费用里 79% 是 API Gateway 请求费。对这种每个请求只做几毫秒计算的应用，API 入口的计费方式比函数代码优化影响更大。
- 单体是固定成本：0.0208 美元/小时，可承载约 200 req/s。a2 优化版在持续请求量超过约 3 req/s（每小时约 1.1 万个请求）时，按请求付费就比一台 t3.small 贵。但单体的这个价格是单机、单 AZ、无高可用的配置；serverless 版本按需扩展，空闲时不产生计算费用，二者的可用性和弹性不对等。

**6. 结论可信度与局限。**
- 单体在两个日期的结果几乎一样（p50、p90 完全相同，吞吐差 1%），说明两天的测量环境可比，a1 v0 与 a2 优化版的差异不是日期造成的。
- 每个版本只测了一次（每遍约 1,870 个请求），p50 和 p90 稳定，但 p99 只由十几个样本决定，波动较大。第 3 节第 2 点的拆分里，第 ② 步只有 2ms，接近单次测量的波动范围，应看作"小幅改善"而非精确值。
- 10 个并发线程远未到单体或 serverless 的容量上限，本报告比较的是低负载下的延迟，不是最大吞吐。
- 缓存的收益是在持续负载下测得的最好情况。流量稀疏时执行环境更常被回收，命中率和收益都会下降。
- a2 的迁移运行中有一次流程违规：S2 首轮子 Agent 读取过 acmeair-a1 的验证材料，事后已按 a2 自身规格重新推导并修正 3 处代码。运行结果已被采用，但 a2 与 a1 并非完全独立。
- Cancel Booking 由脚本条件触发，样本极少（0–4 个），不参与比较。
