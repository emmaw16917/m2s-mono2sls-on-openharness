# Acme Air：单体 vs a1 优化版 vs a2 优化版（AWS 同区域实测）

2026-10-12。数据来自两次实测：`acmeair-ec2-ab/`（2026-10-09，单体 + a1 各版本）和 `acmeair-ec2-a2/`（2026-10-12，单体 + a2 各版本）。两次的测试设置、数据量和负载完全相同，单体在两次里各测了一遍，作为跨日期对照。

## 1. 测试套件与方法

### 1.1 测试套件

Acme Air 官方性能测试驱动 **acmeair-driver**：JMeter 脚本 `AcmeAir.jmx`，附带官方 JMeter 扩展函数（生成航班日期、解析航班查询结果、选择要取消的预订）。脚本与单体同一提交（acmeair-nodejs `11fa31a`），未做修改。

脚本模拟一位顾客的完整会话，每个线程循环执行：

| 步骤 | 请求 | 接口 | 每轮次数 |
|---|---|---|---|
| 1 | Login | `POST /rest/api/login` | 1 |
| 2 | View Profile Information | `GET /rest/api/customer/byid/{user}` | 按比例，约 25% 的轮次 |
| 3 | Update Customer | `POST /rest/api/customer/byid/{user}` | 同上，紧跟步骤 2 |
| 4 | QueryFlight | `POST /rest/api/flights/queryflights`（往返） | 5 |
| 5 | BookFlight | `POST /rest/api/bookings/bookflights` | 查到可订航班时 1 次（单体约 96% 的轮次，serverless 约 82%，取决于查询结果） |
| 6 | List Bookings | `GET /rest/api/bookings/byuser/{user}` | 1 |
| 7 | Cancel Booking | `POST /rest/api/bookings/cancelbooking` | 只在该顾客已有 2 个以上预订时 |
| 8 | logout | `GET /rest/api/login/logout` | 1 |

用户从 1 万个顾客中随机抽取。会话靠 `sessionid` cookie 维持，和单体的登录契约一致。每遍约 1,870 个请求，其中 QueryFlight 1,000 个，占 54%。

### 1.2 测试环境

| 项目 | 设置 |
|---|---|
| 区域 | us-east-1，压测机与被测服务同区域 |
| 压测机 | EC2 t3.small，us-east-1a，JMeter 非 GUI 模式 |
| 并发与轮次 | 10 个线程 × 20 轮（`-JNUM_THREAD=10 -JLOOP_COUNT=20`）；闭环负载，每个线程等上一个响应回来才发下一个 |
| 数据 | 官方 loader 装载：10,000 顾客、14 个机场、394 个航段、5,122 个航班（`MAX_DAYS_TO_SCHEDULE_FLIGHTS=13`，保证往返查询有回程） |
| 遍数 | 每个版本两遍：第 1 遍包含冷启动和冷缓存，第 2 遍为热态 |

### 1.3 被测版本

| 版本 | 部署 | API 入口 | 相对 v0 的优化 |
|---|---|---|---|
| **单体** | EC2 t3.small（Node 22 + MongoDB 4.4，同一台机器，同 AZ） | 应用直接监听 9080 端口 | — |
| **a1 优化版** | Lambda（nodejs22.x、arm64、512 MB）+ DynamoDB 按需计费；工作区 acmeair-a1，提交 `474d8a9` | REST API（`AWS::Serverless::Api`，边缘优化） | S5 规则 R1：`loader-load` 四张表并行写（kept_inconclusive）；`bookings-create` 两条往返预订写入并行（kept） |
| **a2 优化版** | 同上；工作区 acmeair-a2，提交 `838407b` | HTTP API（`AWS::Serverless::HttpApi`，payload 1.0，S1 决定） | S5 规则 R8：`flights-query` 对航班和航段两张表加内存缓存（TTL 1200 秒，最多 10 万条，依据 S1 写入的 bounded_staleness 契约 SI-23） |

a1 和 a2 是同一个单体经流水线两次独立迁移的产物。a2 的流水线增加了 API 类型决策（AT1/AT2）、缓存契约（CT7）和 R1b/R8 规则，此外每个函数的代码也是重新生成的。

### 1.4 测量了什么

- **端到端延迟**：压测机 JMeter 记录的每个请求耗时（JTL），统计 p50、p90、p99 和吞吐量。
- **每接口延迟**：按请求类型分别统计。如果一个请求的耗时窗口内完整包含一次 Lambda 冷启动（INIT_START 到对应的 REPORT，允许 100ms 时钟误差），它就算冷启动样本，不计入每接口的 p50/p90，只单独计数。
- **服务端时间**：
  - 单体：morgan 访问日志记录的每个请求响应时间。
  - Serverless：Lambda REPORT 中的 Duration 和 Init Duration；API Gateway 访问日志中的 responseLatency（请求进入网关到响应离开）和 integrationLatency（网关看到的 Lambda 调用耗时，含调用开销）。
- **资源与费用**：Lambda 调用次数和 GB-秒、DynamoDB 消耗的读写容量单位（RRU/WRU，CloudWatch 按分钟统计，各遍放在不同的分钟里）、按 us-east-1 公开价格计算的费用。
- **正确性**：所有版本两遍都是 0 错误。压测前后用 `config/count*` 接口核对数据量，四次装载结果一致。

## 3. 数据解读

**1. a2 优化版比 a1 优化版快约三分之一，所有接口都受益。**
热态端到端 p50 从 41ms 降到 28ms（−32%），p90 从 60ms 降到 44ms，p99 从 142ms 降到 85ms。闭环负载下吞吐由延迟决定，从 108 升到 130 req/s。七个有足够样本的接口全部变快，降幅 5–17ms。

**2. 提速来自两个独立来源，可以从数据里分开。**
- **API 网关层，所有接口约 −6 到 −9ms。** 网关自身耗时从 4ms 降到 1ms，网关之外的耗时从 6ms 降到 3ms。前者是 HTTP API 比 REST API 轻；后者是 a1 的 REST API 为边缘优化型，请求要经过 CloudFront，而 HTTP API 是区域型端点。除 FlightsQuery 外，各函数的执行时间在 a1 和 a2 之间基本相同（差异 ±1ms），所以这些接口省下的时间都在网关层。之前对 a1 的单变量 A/B（只把 a1 v0 换成 HTTP API）测出 −5ms，与此一致。
- **R8 缓存，只作用于 QueryFlight，额外约 −10ms。** FlightsQuery 函数的执行时间从 24.7ms 降到 13.9ms，读容量 RRU 少了 23%；QueryFlight 端到端从 47ms 降到 30ms，降幅（−17ms）是其他接口的约两倍。由于 QueryFlight 占全部请求的 54%，它是整体 p50 下降最大的贡献者。第 1 遍里 FlightsQuery 的热调用仍是 24.2ms，说明缓存需要时间预热：每个新的执行环境都从空缓存开始。
- **a1 的 R1 优化在端到端看不出效果。** a1 优化版的 BookFlight（37ms）与之前 a1 v0 的 39ms 只差 2ms，在测量波动范围内。

**3. 与单体的差距仍然是一个数量级。**
单体热态 p50 为 2ms，a2 优化版为 28ms，约 14 倍。差距来自架构，而非代码：
- 单体处理一个请求的服务端时间是 0.7–2.5ms，数据库与应用在同一台机器上，没有网络往返。
- Serverless 每个请求至少有 API Gateway → Lambda → DynamoDB 三跳网络。即使函数只做一次 DynamoDB 读取，Lambda 执行时间也有 7–10ms，再加上约 10ms 的调用开销（integration 24ms 减去函数执行时间）和约 4ms 的网关与网络开销。
按现有的优化规则，剩下的空间主要在 DynamoDB 调用次数和串行深度上。R1b（往返查询的去程和回程同时读）测得可再减少约 8ms 的关键路径，但只在缓存未命中时生效。

**4. 冷启动是 serverless 独有的尾延迟来源。**
两个版本第 1 遍各有 27 次冷启动，Init Duration 约 0.3 秒，第 1 遍 p99 达 550–620ms。单体两遍的 p99 都在 10ms 以内。a2 没有针对冷启动做任何改动，两版的 init 时间相近，属于预期。要减少冷启动影响，需要专门的手段（预置并发、缩小部署包、调整内存等），不在本次比较范围内。

**5. 费用：a2 的每请求成本比 a1 低 58%，但在持续负载下仍高于单体。**
- 主要来自 API Gateway 换型（每百万请求 3.5 美元 → 1.0 美元）。DynamoDB 读费用因缓存下降约 7%，Lambda 计算量下降 17%。
- 单体是固定成本：0.0208 美元/小时，可承载约 200 req/s。a2 优化版每百万请求 1.85 美元，当持续请求量超过约 3 req/s（每小时约 1.1 万个请求）时，按请求付费就比一台 t3.small 贵。
- 但单体的这个价格是单机、单 AZ、无高可用的配置；serverless 版本按需扩展，空闲时不产生计算费用，二者的可用性和弹性不对等。

**6. 结论可信度与局限。**
- 单体在两个日期的结果几乎一样（p50、p90 完全相同，吞吐差 1%），说明两天的测量环境可比，a1 与 a2 的差异不是日期造成的。
- 每个版本只测了一次（每遍约 1,870 个请求），p50 和 p90 稳定，但 p99 只由十几个样本决定，波动较大。
- 10 个并发线程远未到单体或 serverless 的容量上限，本报告比较的是低负载下的延迟，不是最大吞吐。
- 缓存的收益是在持续负载下测得的最好情况。流量稀疏时执行环境更常被回收，命中率和收益都会下降。
- a2 的迁移运行中有一次流程违规：S2 首轮子 Agent 读取过 acmeair-a1 的验证材料，事后已按 a2 自身规格重新推导并修正 3 处代码。运行结果已被采用，但 a2 与 a1 并非完全独立。
- Cancel Booking 由脚本条件触发，样本极少（0–4 个），不参与比较。
